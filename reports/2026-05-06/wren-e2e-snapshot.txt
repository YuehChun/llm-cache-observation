## Failure mode encountered: minikube CPU runaway

  After ~2-3 e2e queries through Wren AI's full pipeline, minikube node CPU stayed pinned
  450-2500% for >5 minutes without recovering. K8s API server became unreachable (TLS handshake
  timeout). This was the same class of issue we saw earlier with vllm bench — but worse because
  Wren AI's pipeline is more CPU-intensive (multi-stage inference + ibis-server + qdrant +
  wren-engine all working concurrently).

  Root cause hypothesis: Wren AI v0.29.0's pipeline retries / multi-step planning loop ran
  in parallel and overwhelmed the docker-driver minikube control plane (4 CPU cores allocated).

  Mitigation options:
  1. Increase minikube --cpus from 4 to 6 (would reduce headroom for vllm-metal on host)
  2. Tune Wren AI to be less retry-happy (config.yaml settings)
  3. Use a 7B+ model so each LLM call is meaningful and fewer retries are triggered
  4. Run Wren AI workflow on dedicated hardware

## Final status of e2e test

  - StartSampleDataset succeeded
  - Schema indexing into Qdrant succeeded (27 vectors)
  - First question: failed with ContextWindowExceededError (fixed by --max-model-len 8192)
  - Second question: reached UNDERSTANDING -> SEARCHING -> Ask Retrieval before minikube ran away
  - Task did not reach FINISHED status due to operational instability, NOT due to a logic bug

## Conclusion

  End-to-end Wren AI -> sidecar -> vllm-metal -> Qdrant data flow works structurally:
  - Sidecar captures real /v1/asks routes with route-collapse
  - Qdrant accumulates real vectors from real schema indexing
  - vllm-metal serves real LLM calls and the cache hit rate climbs as pipeline stages
    reuse common context

  The 5-layer dashboard now has REAL Wren AI workflow data on every layer.
  But the workflow is too heavy to run continuously on a 16 GB Apple M3 laptop with
  minikube docker driver — for sustained workload testing, dedicated hardware needed.
