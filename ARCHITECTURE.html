🔬 LLM KV Cache 觀測實驗

以 Wren AI 為真實 workload，於 Apple Silicon 16GB MacBook 上量測 KV cache hit rate、TTFT、prefill 等指標
目標機器：MacBook Apple Silicon, 16GB unified memory 核心模型：Qwen2.5-1.5B-Instruct (MLX, Q4) 更新日期：2026-05-03
🎯 專案目標 📐 架構圖 👁 觀測點 ❌ 排除元件 🧩 元件清單 💾 RAM 預算 🔁 資料流

🎯 專案目標

本專案要回答三個核心問題：

  1. 基線比較：啟用 / 關閉 prefix cache 對 TTFT 與吞吐量的影響有多大？
  2. 真實場景觀察：Wren AI（Text-to-SQL）這種「同 schema、不同問題」的 workload，cache 命中率隨時間如何變化？
  3. K8s 部署研究：把 Wren AI + observability 放到 minikube 上，實際運作所需的最小可行架構長什麼樣？
⚠ 受限於硬體：原始計畫中的 llm-d、Mooncake 因需要資料中心級 GPU（A100+/MI250/TPU v5e+）或多節點 GPU 叢集，無法在 Apple Silicon 16GB MacBook 上運行，已從本架構排除。詳見下方「排除元件」章節。

🔑 為什麼是混合架構（host + minikube）？

  1. vllm-metal 必須在 host：Metal API 是 Apple GPU 的私有介面，無法穿透 Linux container。所以 LLM serving 不能放進 minikube。
  2. Wren AI 與 observability 在 minikube：純 CPU、跨平台，K8s 化沒問題；同時滿足「研究 K8s 部署」的目標。
  3. Prometheus 也放 host（用 Docker Compose）：因為 minikube 在 macOS docker driver 下，host.minikube.internal 解析到的是 Docker Desktop VM 而非真正的 macOS host。把 Prometheus 放 host，直接用 host.docker.internal:8000 scrape vllm-metal 最乾淨。
  4. omlx 作為對照組：用同一個模型在 omlx 上跑，比較 vllm-metal vs omlx 的 cache 行為與 TTFT，附加價值不大但成本很低。

👁 觀測點與目標指標

Prometheus 從 vllm-metal 的 /metrics endpoint 抓 4 大類 cache 指標 + 延遲指標，全部呈現在 Grafana 上。

① 快取命中與查詢（Hit Rate）

最直接衡量 cache 是否發揮作用。命中率 = hits / queries（時間區間滾動）。

  • vllm:prefix_cache_queries — 系統嘗試查詢前綴快取的總次數
  • vllm:prefix_cache_hits — 成功命中前綴快取的總次數
  • PromQL： sum(rate(prefix_cache_hits[5m])) / sum(rate(prefix_cache_queries[5m]))

② KV 區塊駐留與重複利用（Residency）

透過 histogram 採樣，了解 cache 在記憶體中的生命週期。

  • vllm:kv_block_reuse_gap_seconds — 兩次連續存取的時間差
  • vllm:kv_block_lifetime_seconds — 區塊總存活時間（分配 → 驅逐）
  • vllm:kv_block_idle_before_evict_seconds — 被驅逐前的閒置時間（揪出 stranded cache）

③ GPU 空間使用率（Capacity）

Cache 表現與記憶體空間息息相關，逼近 1.0 時 LRU 開始驅逐舊 cache。

  • vllm:gpu_cache_usage_perc — KV cache 區塊使用比例 (0~1)
  • 觀察：當這條線壓到 0.95+ 時，hit rate 通常會下降

④ 延遲與效能驗證（Latency）

Cache 表現最終會反映在推論延遲上，這是「使用者感受到的好處」。

  • vllm:time_to_first_token_seconds — TTFT，cache hit 時應大幅降低
  • vllm:request_prefill_time_seconds — prefill 階段時間
  • vllm:generation_tokens_total — 總產出 tokens（換算 throughput）

❌ 因硬體限制而排除的元件

原始計畫中以下元件因硬體不足無法使用，已從本架構排除。每個排除都有明確理由與替代方案。

🚫 llm-d  硬性無法執行

https://github.com/llm-d/llm-d

llm-d 是 Kubernetes-native 的 distributed LLM inference platform，整合 vLLM + Inference Gateway，主打 P/D Disaggregation 與 Wide Expert Parallelism。

排除原因：llm-d 官方明確要求 NVIDIA A100+ / AMD MI250 / Google TPU v5e+ / Intel GPU Max 等資料中心級加速器，並且依賴 GPUDirect RDMA 才能達到設計效能。Apple Silicon Mac 既沒有這些 GPU，也沒有 NVLink/RDMA 拓撲，連最低門檻都達不到。即使硬塞進去，CRD 也會卡在 readiness check 上跑不起來。

替代方案：本專案改用 單一 vllm-metal 實例跑在 host 上，雖然失去了多節點 disaggregated serving 的研究價值，但 prefix cache、TTFT、KV-block residency 等核心觀測指標都仍可量測。如未來要研究 disaggregated 架構，建議租用雲端 GPU spot instance（GKE/EKS T4 約 $0.5/小時）做 30 分鐘試跑。

🚫 Mooncake (kvcache-ai)  單機環境無觀測意義

https://github.com/kvcache-ai/Mooncake

Mooncake 是 Moonshot AI 為 Kimi 開發的 serving platform，核心是「KVCache-centric disaggregated architecture」—— 把 prefill 與 decoding 拆到不同 cluster，並把 GPU cluster 中閒置的 CPU/DRAM/SSD 池化成共享 KV cache pool。

排除原因：Mooncake 解決的是「我有 32 張 H100 跨節點 KV 互不共用」這種大規模 GPU cluster 的問題。雖然原始碼支援 -DUSE_CUDA=OFF 編 CPU-only，但 ARM64 build 沒被官方驗證，而且單機 16GB MacBook 沒有「跨節點 KV 池化」這個問題可解，跑起來也只是退化成本機 cache，毫無觀測意義。

替代方案：本機環境的 KV cache 觀測，vLLM 內建的 Automatic Prefix Caching (APC) 已經足夠。如果之後想研究分層 cache（GPU → CPU → SSD），改看 LMCache 的 KV offloading 功能（規劃中 Phase 3 條件性實驗）。

⚠️ vLLM 主分支 (CUDA)  部分排除：CUDA 路徑不可用

https://github.com/vllm-project/vllm

vLLM 是業界主流的 LLM inference engine，本專案的觀測指標皆以 vLLM 的 metrics 為標準。

排除原因：vLLM 主分支的 CUDA 路徑在 Apple Silicon 完全不可用（沒有 NVIDIA GPU）。CPU backend 雖然有 ARM64 (NEON) 支援，但要從 source build、效能遠低於 Metal、且需在 ARM64 容器內編譯，整體不划算。

替代方案：改用 vllm-metal plugin（vllm-project + Docker 於 2026/1 合作釋出），它在 macOS host 上直接用 Metal GPU + MLX backend 跑 vLLM 引擎，保留 OpenAI-compatible API 與 Prometheus metrics 介面。限制：只能跑在 macOS host，無法進 Linux container/minikube。

⚠️ LMCache for K8s  延後到 Phase 3

https://github.com/LMCache/LMCache  |  helm repo

LMCache 是 KV cache 分層管理框架，可把 cache 從 GPU 卸載到 CPU/SSD，是本實驗「KV cache 觀測」最有研究價值的元件之一。

延後原因：LMCache 官方文件明指「Linux NVIDIA GPU platform」，Helm chart 與多數 Docker image 都針對 CUDA。ARM64 image 與純 CPU 路徑在搜尋中未確認。

處置：本專案 Phase 1-2 不導入 LMCache，先用 vllm-metal 內建 APC 取得基線觀測。Phase 3（選做）再嘗試在 minikube 內以 --platform=linux/amd64 emulation 跑 vLLM CPU image + LMCache 做對照實驗，但 emulation 慢 5-10 倍，TTFT 數據沒有絕對意義，主要看 cache 行為。
